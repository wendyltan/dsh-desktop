## Design Specificity Verdict

当前界面有中等产品特异性，但没有统一产品世界。“守护之环、鲸鱼标识、DeepSeek 蓝、安静的状态反馈”属于 dsh-desktop；快速提问也体现了桌面 Harness 的独特价值。主窗口却几乎是原样嵌入的 Web Harness，原生辅助窗口则是另一套 SwiftUI 卡片语言。设置、更新、插件管理和恢复跨 Web、菜单栏、App 菜单、原生设置、Guardian 状态窗分散，像两个产品拼接。

确定性扫描真实返回 `[]`、exit 0，但 Impeccable detector 没有 Swift 覆盖声明，也不返回扫描/跳过计数；因此它是“不适用/无证据”，不是 clean scan。原生源码审计为 12/20：平台原生性与语义色基础较好，主要技术债是固定不可缩放窗口、可访问性语义缺口和状态模型混用。

## Overall Impression

最成熟的界面是“当前状态”：正常时安静，异常时渐进披露，高风险操作有明确影响范围和确认。最大机会不是增加装饰，而是把“桌面入口、快速提问、服务保护、插件处置”重组为一个一致的原生控制面，并把 Web 主窗口明确定位为工作区。

## What's Working

1. Guardian 正确区分服务健康、安全模式、恢复中和插件警告；inactive 插件不会被升级成服务故障。
2. 重启、恢复、更新、切换引擎的安全文案成熟，能区分当前服务与候选引擎。
3. 快速提问是高频、桌面原生、价值明确的功能；快捷键、草稿保留、新/已有会话和错误重试都值得保留。

## Priority Issues

### [P1] 插件兼容告警缺少可信的处置闭环

- **Why it matters:** 当前有三个 enabled 插件被标为需检查，但 Guardian 只能展示原始依赖列表。`dsh-at-file` 的 `*` peer 在 prerelease 引擎上被 `semver.satisfies` 判成大量问题，其中许多可能只是检测语义噪声。直接提供下载、停用或卸载会把误报放大成破坏性操作。
- **Fix:** 先把结果分为确认不兼容、依赖缺失、声明范围不匹配、无法解析、仅候选风险；携带 current/candidate、引擎版本、检查时间和来源。原生端第一阶段只提供按插件聚合的解决办法和“在插件页查看”。依赖修复必须等待插件管理后端提供 dry-run、精确版本、快照、preflight 和 rollback 合同。
- **Suggested command:** `$impeccable shape`，随后 `$impeccable harden`

### [P1] 原生控制面与 Web 工作区的信息架构割裂

- **Why it matters:** Web 设置和“DeepSeek Harness 设置”同名；多处“检查更新”实际只更新 Harness 引擎；插件启停、兼容诊断与真正处置位于不同入口。
- **Fix:** 明确两层：Web 是“工作区”，原生是“桌面控制台”。原生设置改名“桌面端设置”，“检查更新”改为“检查 Harness 引擎更新”。插件告警直接深链到对应插件详情。
- **Suggested command:** `$impeccable distill` / `$impeccable clarify`

### [P1] 辅助窗口固定尺寸且关键可访问语义不完整

- **Why it matters:** Settings、Quick Prompt、Guardian 和 sheets 都不可缩放；大字号、长中文错误与依赖列表容易裁切。Quick Prompt 编辑器缺少明确 VoiceOver label，异步状态不主动播报。
- **Fix:** 固定尺寸改为 min/ideal size，窗口允许增长；正文滚动、底部动作固定；补编辑器、图标按钮、快捷键录制和异步阶段的 accessibility label/value/announcement。
- **Suggested command:** `$impeccable adapt` / `$impeccable audit`

### [P2] 快速提问成功路径没有收尾

- **Why it matters:** 成功后浮窗立即关闭，“打开刚发送的会话”被转移到菜单栏，用户无法确认目标会话。
- **Fix:** 保留 1–2 秒成功态，显示目标会话与“打开会话”；菜单栏入口作为兜底。
- **Suggested command:** `$impeccable polish`

### [P2] 错误与状态来源混在一起

- **Why it matters:** Guardian 操作错误可能被随后 status refresh 覆盖；candidate 兼容结果可能长期遮住 current。底层英文系统错误会直接进入用户横幅。
- **Fix:** 分离 status error、operation error、current compatibility 与 candidate compatibility；错误统一为“发生什么 / 影响什么 / 立即动作”，底层详情折叠。
- **Suggested command:** `$impeccable harden` / `$impeccable clarify`

## Persona Red Flags

**Alex（高频专业用户）**：快捷键高效，但插件告警没有可执行路径；依赖逐条展示却无法按需要处理/可忽略过滤；快速提问发送后目标会话入口隐藏。

**Jordan（首次使用者）**：无法理解 Web 设置与桌面端设置的边界；Harness 引擎、Guardian、预检、Web profile 缺少就地解释；“可能不兼容”会被误解为服务已损坏。

**Sam（辅助功能用户）**：状态不只依赖颜色是优点；固定窗口、TextEditor 缺少 label、异步状态无播报、删除图标仅靠 help、长依赖组超长朗读是风险。

## 功能去留

- **保留并强化：** Web 主客户端、快速提问、当前状态/守护之环、恢复/预检/引擎切换、菜单栏待处理审批。
- **合并：** 多处引擎更新入口的语义；顶部插件告警与下方重复卡片；发送成功与“打开刚发送的会话”。
- **降级：** 菜单栏余额建议默认关闭；未启用插件保持折叠；原始 peer dependency 列表进入“技术详情”；事件时间线继续只露出最近五条。
- **不建议删除：** 暂无证据表明核心大功能无用；问题主要是重复、命名和位置。
- **删除候选：** 仅限开发测试菜单项“发送会话导航测试通知”，若正式构建仍可见，应移出正式菜单或受调试开关控制。

## 插件兼容处置结论

**Verdict：做，但分阶段。**

最小有用版本不是“三按钮一键修复”，而是每个 enabled 插件一个“安全处理…”入口：先诊断分类，只给一个推荐动作，说明影响与可逆性，再进入现有 Harness 插件页。

1. `checked=false`：只允许重试检查/查看诊断。
2. inactive：保持停用，不升级为服务故障。
3. enabled + confirmed incompatible：主动作“查看解决办法”，二级动作“暂时停用”；绝不自动停用。
4. missing/unresolved：写“无法解析依赖”，不称为不兼容，不推荐卸载。
5. candidate：明确当前服务未变，任何方案绑定候选引擎版本。
6. Guardian busy：禁用插件写操作，不打断恢复或更新。

**下载/更新：** 不允许裸 `npm install`；精确来源和版本；先隔离安装和 smoke test；快照后应用，失败回退。

**暂时停用：** 复用 Harness 插件管理；保留安装包、设置和快照；明确失去的能力与是否重启；提供重新启用。

**移除：** 只放二级菜单；先停用观察；二次确认；说明配置、缓存和数据是否保留；不清理共享依赖；不批量移除。

**明确延期：** 批量自动修复、自动禁用、自动删除、候选结果直接修改当前 profile、未经隔离验证的依赖安装。

## Proposed Refactor Direction

把产品重构成“原生桌面控制台 + Web 工作区”而不是继续做一组独立浮窗：

- **菜单栏：** 仅保留快速提问、待处理、打开工作区、系统健康摘要；余额默认进入菜单内。
- **快速提问：** 作为桌面会话启动器，有明确成功态与最近目标。
- **桌面控制台：** 概览、插件与兼容、恢复与版本、桌面端设置四个任务域；正常态安静，异常态按插件/操作聚合。
- **Web 工作区：** 保留完整聊天、会话、插件目录和插件管理，不在 SwiftUI 重造聊天或第二套插件写路径。

视觉上采用 Operate 模式：一个系统字体家族、紧凑尺度、系统材质和语义色；DeepSeek 蓝只用于主动作、选中和状态，不作装饰。保留鲸鱼与守护环作为唯一品牌记忆点，减少通用 Sparkles 和重复卡片。

## Minor Observations

- 打开 Guardian 面板会重复执行两次 deep refresh，应保留 AppStore 为唯一刷新所有者。
- 品牌蓝应成为 light/dark/high-contrast 命名颜色资产。
- 设置页应说明哪些改动立即生效。
- 插件页中英文描述混排降低完成感。
- 固定窗口风险、VoiceOver、大字体和深色模式仍需专项实测。

## Questions to Consider

1. 桌面端的首要身份应是“快速入口”还是“完整控制台”？
2. 插件兼容流程第一版是否只做可信诊断与深链，还是必须同时支持安全停用？
3. 当前主窗口的 Web 工作区是否应保持主体，原生端只负责控制，还是希望逐步把更多管理页迁到原生？
